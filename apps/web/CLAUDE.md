# Web app (`@app/web`)

React 18 + Vite + Tailwind 3 + react-router 7. Full rules: `docs/standards.md` (Frontend).

- **Data**: every call goes through `src/lib/api.ts` (`VITE_API_URL`, default same origin). Types and Zod schemas come from `@app/shared`; never redeclare them. Server state never goes in `localStorage` (UI prefs only: theme, panel width/tab).
- **Sign-in**: `features/auth/AuthGate` wraps the routes. It reads `GET /v1/auth/config`; with sign-in off it renders the app as before. With it on it builds a Supabase client (supabase-js, which keeps the session in this browser), registers `setAuthHandlers` in `lib/api.ts` (every request sends `Authorization: Bearer <access token>`, renewed by `getSession`; a 401 signs out locally), and, when the config says `isRequired`, shows `LoginPage` until there is a session. Otherwise (the default) the app opens as a guest (no token sent) and `LoginPage` shows only once the user asks (`useAuth()` is `{ kind: 'guest', signIn }`; the sidebar foot's Sign in row and `ConnectionMenu`'s Sign in), or after a failed Google / email-link return, with Continue without signing in under it; signing out, or a 401, goes back to guest. `LoginPage` is a split screen (`AuthCard`: brand panel from `lg`, form column) with Sign in / Create account tabs, Continue with Google (`signInWithOAuth`, shown only once the project's public `/auth/v1/settings` says Google is on, so it never flashes), email and password (show/hide, strength meter on sign-up), Forgot password (`resetPasswordForEmail`), a Check your email step with a 60 s resend, and Supabase errors in plain words with a next step (`authErrors.ts`). `AuthGate` reads the URL first: a failed Google or email-link return shows its error on the login page (then leaves the URL), and a reset link (`type=recovery`, or the `PASSWORD_RECOVERY` event) shows `SetPasswordPage` before the app. Offline tests: `apps/web/test/auth-login.test.ts`. After a session, it checks `GET /v1/auth/me` (a 403 shows No access with Sign in with another account, and Continue without signing in when optional). `useAuth()` (`authContext.ts`) gives `{ kind: 'signedIn' }` with the user, the provider's `profile` (name and https photo from the Supabase user's metadata, `profileOf`) and `signOut`, or the guest (null with sign-in off). `features/auth/AccountMenu` sits at the very foot of `ChatSidebar`, below the workspace switcher: photo (from `*.googleusercontent.com`, allowed in the API's CSP `img-src` when sign-in is on) or initials, name and email, and a menu opening upward with Sign out (a Sign in row for a guest); `ConnectionMenu` also has Sign out (or Sign in). Attachments come with the sign-in, so `AttachmentImage` shows sent images from blob URLs and a sent file's chip downloads it (`fetchAttachment`, `requestBlob`); no API URL goes in an `<img src>` or link.
- **Answers**: agent text renders through `components/Markdown.tsx` (`react-markdown` + `remark-gfm`: CommonMark and GitHub tables, task lists, strikethrough, autolinks). It builds React elements, shows any HTML in the text as plain text, opens links in a new tab, shows images as links, and colours JSON code blocks (`CodeText`). `components/CopyButton` copies a message: under a user bubble (on hover/focus, always on touch screens), and at the start of a finished reply's steps line (its answer text as Markdown, without interim notes or errors).
- **Plans**: shown in the conversation, not the side panel. A `create_plan` call leaves a `plan` flow item (`conversation.ts`); `planPlacement.ts` matches each to the chat's plans (`earlier` then current), and `AgentMessage` draws a `PlanCard` there. Steps show inline: an `update_plan` that starts a step (or finishes one never started, or names a `next_step`) leaves a `step` flow item, and `flowSections.ts` groups the tool calls, interim text and approvals after it under that step's `PlanStepSection` (number, status, text, note) until the next step, plan, note, answer or error. A plan with inline steps gets a short card (goal, progress, Done when); one without (older chats) keeps the foldable full list (`EarlierPlan`). The current plan's live progress is also in `PlanDock` above the composer (shown while it has open steps or the agent works on it). `add_plan_steps` leaves a note. The run's planning step leaves a `thought` flow item at the start of the reply, drawn by `ThoughtLine` as "Thought for 12s" once it decides (timed live from the `planning` to the `route` event; after a reload, the `planner` call's `durationMs` in the `meta` item). Offline tests: `apps/web/test/plan-steps.test.ts`, `apps/web/test/thought.test.ts` (`npm run test -w @app/web`).
- **MCP**: servers are set up in Settings → MCP servers (`features/mcp/McpServersPage`, form at `/settings/mcp/new` and `/settings/mcp/:name/edit`); a workspace turns them on in its settings form (`McpServerSwitches` in `features/workspaces/AgentChoices`, saved after the workspace with `PUT …/mcp/enabled`); the side panel's MCP tab (`McpPanel`, in its lower section) lists only the servers on there, one compact `McpServerRow` each (dot, name, tool count that folds open the tools with Always allow, restart and edit on hover, a switch to turn it off), and reloads when the workspace form saves.
- **Context window**: the model form (`features/models/ModelFormPage`) has an optional Context window field with 32K / 128K / 200K / 1M quick picks (empty: 128K). The chat state keeps the last `context` event (`ConversationState.context`), shown by `ContextMeter` at the end of the composer's token line (a thin bar and "Context 42% of 200K", amber from 80%, where summarizing starts); a `compaction` event, or a `compaction` history item after a reload, adds a note in the chat where older messages were summarized (they still show).
- **Token usage**: the token counts on each reply's steps line and on the composer's token line are buttons (dotted underline, `TOKENS_BUTTON` in `AgentMessage`); both open `features/chat/TokenUsageDialog` (state in `ChatView`). From a reply: each model call (`RunResult.calls` / the history `meta` item's `calls`: kind, model, duration, tools asked for, tokens). From the chat: each message's total (`tokenUsage.ts` `messageUsages`, labelled with the message that started the run), folding open to its calls. Bars split cached input / new input / output in `--usage-*` colours (`bg-usage-*`). Each call also carries what its tokens went to (`input` / `output`: `TokenGroup`s, estimated by `@app/agent`'s `usage-breakdown.ts`); `Composition` shows them as share bars, per request (its row folds open) and added up for the reply or chat (`mergeGroups`, so a result re-sent on each step counts each time). Replies saved before calls were recorded show their total only. Calls marked `isEstimated` (the server reported no tokens) say "estimated" in their row and the footnote explains it. While a run works, its `usage` events count live: the reducer adds what's new since the last one to the chat's total (`runUsage` holds the run's so far, so `done` doesn't count it twice) and the reply shows "2 steps · 12K tokens" (`liveMeta`) under its status until the final steps line replaces it. Offline tests: `apps/web/test/token-usage.test.ts`.
- **Runs**: `POST /v1/runs` is read with `src/lib/sse.ts`. `features/chat/conversation.ts` is the reducer that turns saved history and `StreamEvent`s into what the chat shows; `useConversation` owns the stream.
- **Questions**: a `question` event (the agent's `ask_user`) sets `ConversationState.question`, and `ChatView` shows `QuestionPrompt` over the message box (keyed by id): the question, its options numbered (click, the number key, or ↑↓ and Enter), a Something else… box for the user's own words, and Skip (Esc). It's compact (options on one line each, label · description; the list scrolls past 45vh) and a chevron minimizes it to a one-line bar (icon, truncated question, Skip) that expands on click; it stays open meanwhile. The keyboard goes to it when it opens and on each expand. `useConversation.answer` posts to `POST /v1/questions/:id` (`question_sending` / `question_failed` / `question_answered`); `question_closed`, `done`, an error or the run finishing close it. The tool call stays in the reply as an ordinary tool row (question icon) whose result says what was picked. In voice mode `VoiceBar` says once that there's a question (`waitingFor: 'answer'`). Offline tests: `apps/web/test/questions.test.ts`.
- **Steering**: while this tab's run works, the `Composer` stays enabled (`onSteer`): Enter / the teal Send next to Stop posts the text to `POST /v1/chats/:id/run/messages` (`useConversation.steer`; files and picked skills stay in the box). Until the agent reads it, it's listed above the box in `ChatView` (`queued`); its `steer` event removes it there and adds a user turn (`isSteer`, "Sent while the agent worked" under the bubble) followed by a new agent turn, so the run's steps line ends up under the last one (history items with `steer: true` draw the same). Messages still unread when the run ends, or refused, go back into the box (`returned` → `restoreDraft`) with a warning toast. Voice mode doesn't steer (it has Interrupt). Offline tests: `apps/web/test/steering.test.ts`.
- **Routes** (`src/App.tsx`): `/settings/models`, `/settings/models/new`, `/settings/models/:id/edit` (app-wide models), `/settings/agent` (app-wide agent settings; `SettingsTabs` switches between the two), `/workspaces/new`, `/workspaces/:id/settings`, `/settings/mcp`, `/settings/mcp/new`, `/settings/mcp/:name/edit` (form pages using `usePageHeader` + `Topbar`), `/workspaces/:id` and `/workspaces/:id/chats/:chatId` (the chat screen, one parent route so it stays mounted when a new chat gets its id).
- **Side panel**: `features/panel/SidePanel` (the Files tree uses VS Code's UI font, `font-explorer` in `tailwind.config.js`, 13px, compact rows, and fades what git ignores, `WorkspaceFiles.ignored`, a folder's contents too): Files, Terminal, Git diff and Tasks as the top tabs (Terminal and Git diff each only where the workspace's Planning & tools tab turns it on under Side panel tabs, `hasTerminalTab` / `hasGitTab`, both off by default; `visiblePanelTabs` in `panelTabs.ts`, and `ChatScreen` shows Files when the remembered tab is hidden; their icons hide when the strip is under 400px; `tasks/TasksPanel`: a `$` command box on top (Enter or Run starts it in the background in the workspace folder via `POST …/tasks`, toasts, opens its output; errors such as a refused command show under the box), then the background tasks running, the agent's and the user's, from `useRunningTasks`, which `SidePanel` polls every 10 s while the browser tab is showing (paused while hidden, `lib/usePageVisible`; the git change count and an open task's output pause too) and on each run start/end so the tab shows a running count; each row has a live dot, the command, its folder, elapsed time and Stop (`DELETE …/tasks/:taskId`, toast), and opens its output, fetched every 1.5 s and following the end; only running tasks are listed, so a stopped one drops off; `files/FilesPanel`: a search toolbar, Name or Content, via `GET …/files/search` in `useFileSearch`; a result opens `FilePreview` at the matching line. `FilePreview` edits too: Edit swaps in `CodeEditor` (CodeMirror 6, lazy-loaded with its language modes, coloured with the same `hljs-*` classes), Save / ⌘S sends `PUT …/files/content` with the version it opened, and a 409 offers Reload or Overwrite; unsaved edits ask before closing. New files and folders come from the toolbar or a row's ⋯ menu / right-click (`RowMenu`: New file, New folder, Reveal in Finder, Rename, Delete). Reveal (`files/revealLabel.ts`: Reveal in Finder / Reveal in File Explorer / Open containing folder, picked from the browser's system, which is the API's) calls `POST …/files/reveal`; the toolbar's ⋮ reveals the workspace folder. Naming is inline in the tree with `NameInput`: a new entry's box is the first row inside its folder (`POST …/files`), a rename replaces the row (`PATCH …/files`) and delete asks in `ConfirmDeleteDialog` (`DELETE …/files?path=`); `git/GitPanel`: changed files since the last commit, each opening its diff in `DiffView` with line numbers and both sides syntax-highlighted; reloads when a run ends and every 10 s while the browser tab shows (`GIT_POLL_MS`, the tab's count too; open diffs load again only when the list changed, and the refresh button spins only for a reload the user asked for); the API logs these polls and the task polls at debug only (`POLLED_ROUTES` in `http-logging.ts`)); below them `LowerPanel` holds Skills (first, the default), Memory and MCP in their own tabs (`features/skills/SkillsPanel`: the workspace's skills, each opening the `SkillDialog` popup, as does New skill here and in the composer's Skills menu, through `SkillDialogProvider` / `useSkillDialog` around the chat screen, which also updates the list; closing with unsaved changes asks first; its Improve button rewrites the instructions via `POST /v1/prompts/skill` and fills an empty description with its suggestion, with Undo; delete behind `ConfirmDeleteDialog`) (its top edge drags to resize, double-click resets, the chevron folds it to its tabs; tab, height and fold are UI prefs).
- **Tool inputs**: each finished tool call's row shows its tool's own icon (`features/chat/toolIcon.tsx`: a map by tool name, a server for `mcp__*` tools, a wrench for anything else; spinner while running, cross on failure). `features/chat/ToolInput` shows a tool's arguments by kind: `write_file` as highlighted code, `edit_file` as a diff, `run_command` as a shell line, everything else (MCP tools too) as `InputFields`, a labelled list (long text in a box, Markdown rendered when it looks like Markdown, lists as chips, nested data as coloured JSON) with a Raw JSON toggle. Never show the raw argument JSON by default.
- **Voice mode**: a workspace's Chat mode (Voice tab, `ChatModeChoice`) saves `voiceMode`. With Voice picked, the tab shows `features/workspaces/VoiceSettings`: microphone (`useMicrophones`: `enumerateDevices`, Allow access when names are hidden), voice (with Play sample), speed and pitch. They're this browser's UI prefs (`chat/voicePrefs.ts`: `agent.micId`, `agent.voiceName`, `agent.voiceRate`, `agent.voicePitch`), written when the form saves; `useVoicePrefs` keeps open hooks current. `startRecognition`'s `micId` opens that mic with `getUserMedia` and hands its track to `recognition.start(track)` (Chrome 135+), falling back to the default mic. When on, `ChatView` shows `VoiceBar` instead of the `Composer` (a status pill with a call timer and the caption; round call controls on the right: Start voice chat when idle, Send while listening, Interrupt while replying, and a red End call with a hang-up icon always last; the chat's token line, `ChatUsageLine`, shared with the `Composer`, under it) (the composer stays, with a note, where the browser lacks speech recognition or synthesis). One button starts a live conversation: `startRecognition` (in `useSpeechInput`) listens continuously and a 1-second pause (`SEND_AFTER_PAUSE_MS` in `VoiceBar`, restarted by every word heard; the browser's own end-of-speech cut in too soon) sends it as a normal message (8 s with nothing heard ends the conversation); the reply is read aloud as it streams (`useConversation`'s `subscribeReply` gives the raw text deltas and a `break` at each tool call; `speechText.ts`'s `createSpeechSplitter` hands back finished sentences without code or Markdown; `useSpeechOutput` queues them on `speechSynthesis` in the most natural voice for the page language (Natural / Premium / Enhanced, then Google; the workspace settings' Voice tab overrides it, saved as the `agent.voiceName` UI pref; the bar has no voice picker)), then it listens again. The mic is only on while it's the user's turn (listening while the reply plays let the speakers' echo interrupt it, and opening the mic mid-reply made the voice drop out): the coral Interrupt button, shown while it replies, stops speech and the run and listens; what's said is sent once the run has stopped. While it waits on the agent (Thinking: no speech, no approval pending, not stopping) `useThinkingSound` loops the bubble-pop clip `public/sounds/thinking.mp3` with Web Audio (decoded once, gapless `loop`, one shared `AudioContext` suspended while silent; it starts only after a short delay so the gaps between spoken sentences stay quiet, and fades out). The chat keeps pace with the voice: each `SpokenSentence` from the splitter carries where it ends in the reply's raw streamed text (across tool-call breaks, code blocks mapped past), and as it starts being said `VoiceBar`'s `onSpokenUpTo` lets `ChatView` show the newest `AgentMessage`'s text blocks only up to there (`revealUpTo`; tool steps and approvals show at once; null shows all once speech ends, is interrupted, or the bar listens). The sentence being read shows as a caption in the bar; nothing in the chat is marked and words aren't tracked (per-word highlighting ran work on every spoken word and was removed while chasing choppy, robotic-sounding speech). Approvals are announced once and wait for a click (no cut-in listening meanwhile). A text box under it takes a pasted link or note: it's added after the next spoken message (then cleared), or Enter sends it on its own (cutting in like speech).
- **Workspace form tabs**: `WorkspaceFormPage` splits into General (name, folder, delete), Instructions, Planning & tools, Voice and MCP servers tabs (one form, every tab stays mounted so nothing typed is lost; a failed check switches to the tab with the error; arrow keys move between tabs). The tabs are a vertical column beside the form from `md` up (sticky while it scrolls, the same look as the Preferences side tabs), a scrolling row above it on phones. The settings popup is `Modal size="xl"` (up to 1240px wide, a fixed `min(820px, 88vh)` tall so switching tabs doesn't resize it; longer content scrolls inside).
- **Workspace agent choices**: the workspace form's Planning (`Agent settings` / Agent decides (`off`) / Planning step (`auto`)) and Tools switches (`features/workspaces/AgentChoices`) save `planning` and `disabledTools`; Plans off disables the Planning choice. Settings → Agent's "Planning step before every message" switch sets the app-wide mode (off by default). A new workspace starts with `DEFAULT_DISABLED_TOOLS` (`@app/shared`: Files off, so the file tools are turned on by hand). Its MCP servers section lists the app's servers with a switch each.
- **Instructions assistant**: the workspace form's instructions box is `features/workspaces/InstructionsEditor` (textarea plus an attached AI bar: a request box, Write/Rewrite, one-click chips, Undo); it calls `POST /v1/prompts/instructions` and only fills the box, so the user still reviews and saves.
- **Settings popup**: opened from the chat screen, Models, Agent and MCP servers (and their forms) and the workspace form (`/workspaces/new`, `/workspaces/:id/settings`) show in a popup over the chat (`layout/SettingsModal`): `useSettingsBackground` keeps the chat's location as the background while the URL is one of those pages, and `App` renders the routes at the background plus the same `settingsRoutes` / `workspaceFormRoutes` inside `SettingsModal` (`Topbar inModal`). For the app settings (`/settings/*`) the popup lays them out with `SettingsSideTabs` (`features/settings/SettingsTabs`): Models, MCP servers and Agent settings as vertical tabs on the left (a scrolling row on phones), a sub-form keeping its tab selected; there each page's own horizontal `SettingsTabs` hide (a context), and they stay on full pages. One opened directly or reloaded is a full page. Close goes back to the chat; saving a workspace goes back to the chat it was opened from (`from` state) and `announceWorkspaceSaved` makes the mounted chat screen reload the workspace. A form's buttons go in `FormActions` (`layout/pageHeader`): in the popup's footer bar (Delete / Reset on the left, Cancel and Save on the right), in the top bar on a full page; list pages keep `TopbarActions` at the top, and an empty footer stays hidden. `Modal` closes on Escape only when it's the topmost popup (the folder picker opens over the workspace form).
- **Patterns**: forms on their own pages (skills and the settings popup above are the exceptions, as the user asked); deletes behind `ConfirmDeleteDialog`; a toast after every save, rename and delete (`lib/toast`: `toast(message, kind)` with `success` (default), `error` for failures, `warning` for partial saves or things gone missing, `info`; bottom-right, dismissable, paused on hover, errors stay longest); the URL reflects the open workspace and chat.
- **Look**: every page sits under `layout/AppNav`: brand / workspace switcher as a breadcrumb, then the connection chip (`ConnectionMenu`: approvals, folder, links to Models and Agent settings), theme and workspace settings (`WorkspaceSettingsLink`). On the chat screen at `xl` and up there is no top bar (`AppNav hasSidebar`): `ChatSidebar` carries the brand (`BrandLink`) and the open workspace's name at its top, with its real folder path under it (`WorkspacePath`: as the system writes it, `/` separators, its own folder in bold, scrolled to the end), and Workspace settings and New workspace links (`SidebarLinks`, greyed while the agent works) and the workspace switcher (`WorkspaceSwitcher variant="sidebar" opensUp`, a "Switch workspace" button whose menu opens upward, sorted by recent activity, `lastActiveAt`; only the top-bar variant's menu repeats those two links) at its bottom; the app-wide settings open from the footer's Preferences, which also shows an auto-approve / refuse badge when approvals aren't "ask"; the theme toggle (`ThemeToggle size="sm"`) sits after Preferences at the right end of the footer. Below `xl` the bar stays, since it opens the sidebar drawer. At `xl` and up a dedicated workspace column sits left of the chats sidebar (`features/workspaces/WorkspaceSidebar`, the grid's first track `--workspaces-col`): brand at its top-left (so `ChatSidebar`'s header shows a Chats label instead and `ChatHeader` never takes the titlebar inset), a search box, every workspace (avatar, name, chat count, sorted by recent activity, greyed while the agent works) and, at its foot, New workspace, Install app and the offline warning (`SidebarLinks only="app"`) and `AccountMenu` (Sign in / the signed-in user); the collapsed rail keeps New workspace as an icon. Workspace settings stays at the foot of the chats sidebar (`SidebarLinks only="workspace"`). Below `xl` the chats drawer shows all the links and the account row. Workspaces can be collected in sidebar folders (`WorkspaceGroup`, saved server-side via `/v1/workspace-groups`; a workspace's `groupId` files it): the folder-plus button by the Workspaces label makes one (inline name, `FolderNameInput`), each folder opens and closes (closed ids remembered as `agent.workspaceFoldersClosed`) and has a ⋯ menu to rename or delete it (its workspaces move back to the top level, never deleted); a workspace moves into or out of a folder from its ⋯ menu or by dragging its row onto a folder or the top-level list (`WorkspaceSidebarRows`; the arranging and search is the pure `workspaceFolders.arrangeWorkspaces`, tested in `test/workspace-folders.test.ts`). A search shows matching workspaces and every workspace of a folder whose name matches. It collapses to a 64px avatar rail and back (remembered as `agent.workspacesCollapsed`; the rail lists every workspace, without folders); `ChatSidebar`'s Switch workspace button shows only in the drawer below `xl`. `SidebarResizer` measures from the chats sidebar's own left edge. A 32px footer runs along the bottom of the chat screen (a second row of `ChatScreen`'s grid; at `xl` the chat list spans both rows, so the footer starts after it) with a small Preferences link (gear + text, `features/chat/PreferencesLink`) at its right end that opens the app settings popup on Models. Voice input: the composer's mic (`features/chat/useSpeechInput`, the browser's Web Speech API, one utterance: it ends when you pause) puts the words after what's typed, never sends them; hidden where the browser has no speech recognition (Firefox). Chrome turns speech into text on Google's servers. Files are attached in the composer (paperclip, drop or paste; `useDraftAttachments` uploads each one at once to `POST /v1/workspaces/:id/attachments`, the run sends their ids) and shown in the sent message by `UserMessage` / `AttachmentChip`. The model and reasoning effort are picked per message in the composer (`features/chat/ModelControls`, remembered by `useModelChoice` as a UI preference). The Notes tab (`features/panel/notes/NotesPanel`, a top side-panel tab right after Tasks, always shown; list from `useNotes`, loaded in `SidePanel` and reloaded when the tab is picked) holds the user's own notes for the workspace (`GET/POST /v1/workspaces/:id/notes`, `PUT/DELETE …/notes/:noteId`, saved by `@app/db`'s `WorkspaceNotes` as notes.json in the workspace's data folder; the agent doesn't see them): newest change first, a search from four notes, and `NoteEditor` in the tab itself (title and text, Save or Ctrl/⌘+Enter, delete with `ConfirmDeleteDialog`, a toast after each, and leaving with unsaved changes asks first). Its pure list logic is `notes/noteList.ts` (tested in `test/notes-tab.test.ts`). The Agents tab (`features/agents/AgentsPanel`, next to Skills in `LowerPanel`, list from `useAgents`: `GET /v1/workspaces/:id/agents` returns `{ specialists, problems }`) lists the workspace's own specialists (edit, delete; a "replaces built-in" badge), then the built-ins (click: a new one filled from a copy), and above them the agents-folder files that couldn't be used, each with its reason, Fix (`AgentDialog` in `fix` mode rewrites it; a badly named file is saved under the tidied name and the old file deleted) and delete. `AgentDialog` edits name, when to use it, tool groups, read-only, model and role; the form's pure logic is `agentDraft.ts` (tested in `test/agents-tab.test.ts`). Skills are picked per message with `SkillPicker` (next to the wand; `ChatScreen`'s `useSkills` feeds it and the Skills tab), shown as `SkillChip`s above the box and on the sent message, and sent as `skills`. Next to them, while approvals are set to ask, `AutoApproveToggle` (remembered as `agent.autoApprove`, shown in warning colours while on) sends `autoApprove` with each message and, flipped during a run, applies it there too (`changeAutoApprove`). Style: teal and navy on a soft mint white (tokens in `index.css`, `--accent` teal, `--ink` navy, `--coral` for warm highlights), Inter (`@fontsource-variable/inter`, set as `--font-sans` in `index.css`), bold headlines with a `.highlight` word, `.tag` pill labels and `.step-number` tiles. Corners follow one scale, `--radius-card` / `--radius-control` / `--radius-small` / `--radius-tiny` in `index.css`, which Tailwind's `rounded-2xl` / `xl` / `lg` / `md` read (avoid one-off `rounded-[…]` values). Cards are rounded `.panel`s with a soft `shadow-card`; `shadow-float` / `shadow-dialog` for menus, drawers and dialogs; `shadow-accent` under teal buttons. Status colour goes through `components/Badge` (pills) or a left border, not filled cards.
- **Install as an app**: a web app manifest (`public/manifest.webmanifest`, linked from `index.html`) with icons in `public/icons/` (`icon.svg` and `icon-maskable.svg` are the sources; the PNGs were rendered from them with headless Chrome at 192/512/180 px). No service worker: Chrome doesn't need one to install, and the app must always talk to the live API. `lib/installApp.ts` keeps Chrome's `beforeinstallprompt` (started in `main.tsx`) so `SidebarLinks` shows Install app while Chrome offers it.
- **Desktop window**: in the Electron app (`apps/desktop`) `public/theme-init.js` sets `data-desktop` from the preload's `window.hamroDesktop`. On macOS there's no title bar, so top bars carry the `titlebar` class (they drag the window; their controls don't) and the one at the top-left adds `var(--titlebar-inset)` to its left padding (`ChatSidebar`'s header, `ChatHeader` while the sidebar is collapsed at xl, `AppNav`). A new full-width top bar needs both. `--titlebar-inset` is 0px in a browser, so these are no-ops there.
- **Theme**: light/dark/system via `src/lib/theme.tsx` as `data-theme` on `<html>`; colours from the CSS variables in `src/index.css`. `public/theme-init.js` applies it before first paint (a file, not inline, because the API's CSP blocks inline scripts).
- **Dev**: `npm run dev` (root: API and web together) or `npm run dev:web` on :5173 proxies `/v1` to the API on `127.0.0.1:<PORT>` (the root `.env`'s `PORT`, default 4000, read with `loadEnv` in `vite.config.ts`). `npm run build -w @app/web` outputs `dist/`, which the API serves.
