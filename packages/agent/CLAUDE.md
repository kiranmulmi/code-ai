# Agent core (`@app/agent`)

The agent itself, with no HTTP and no database. `src/index.ts` is the public API used by `@app/db`, `@app/api` and `@app/cli`.

- `agent.ts`: the loop. Plan (by default the model calls `create_plan` itself when a task has several steps; with `planning: 'auto'` a planning step, one extra tool-free call, decides direct vs plan first), act (model + tools), check (open plan steps go back once), limit (a tool-free summary when out of steps or tokens). A step's tool calls run in the order asked, except that read-only calls next to each other (`isReadOnly` built-in tools; never MCP tools or ones that ask first) run at the same time (`batchCalls`); their results go back in the order asked. A call with the same tool and arguments that gets the same result as last time comes back with `REPEATED_CALL_NOTE` (`noteRepeat`), so a stuck model changes course before the step limit.
- `guardrails.ts` `Budget`: `maxSteps` counts working steps only (`kind: 'step'`; the planner, summaries and the write-up at the limit are listed in `calls` but aren't steps), and `maxTotalTokens` counts input read from the server's cache at `CACHED_INPUT_WEIGHT` (a tenth), since every step resends the conversation.
- `planner.ts`: the planning decision and plan state (`update_plan`'s optional `next_step` starts the next step in the same call, since each plan update otherwise costs a model call). `prompt.ts`: every prompt the model sees. Its "How a request is handled" line follows the planning mode (`hasPlanningStep`, true for `planning: 'auto'`): with the planning step it says a plan may be made before the turn; without it, the model is told to call `create_plan` itself for multi-step work (its plan gets the same check, since a successful `create_plan` sets `planThisRun`).
- `llm.ts`: the only file that calls the model (OpenAI Chat Completions, streamed). `createModelCaller(settings: ModelSettings)` returns a `CallModel`. The model is not in `AgentConfig`: apps pass it per run as `createAgent({ model })` (from `@app/db`'s `store.models`). Tests pass a fake `callModel`. Token counts come from `readUsage`: `inputTokens` is always the whole input, with `cachedInputTokens` (read from the server's prompt cache) and `cacheWriteTokens` beside it, from either OpenAI's `prompt_tokens_details.cached_tokens` or Anthropic-style `cache_read_input_tokens` / `cache_creation_input_tokens` (some proxies leave writes out of `prompt_tokens`; it adds them back). The servers cache on their own; keep the prompt prefix stable (no timestamps, fixed tool order, append-only conversation) so they can.
- `guardrails.ts`: input checks, step/token budget, the file sandbox (`resolveInWorkspace`, `assertCanChange`, `prepareWorkspaceFolder`, `APP_DATA_FOLDER`), the command backstop (`refuseCommand`, `commandEnv`), secrets (`isSecretFile` keeps .env / .mcp.json / keys out of read_file, search_files, copy_path, move_path; `refuseSecretAccess` keeps the agent's run_command out of `~/.code-ai/`, not the user's terminal; `redactSecrets` masks tokens in every tool result and error in `runTool`, before the model, chat, stream and log), the private-address block (`assertPublicUrl`), CLI approvals.
- `config.ts`: `loadAgentConfig(env)`. The only place env is read, and only when an app calls it: just `AGENT_LOG_DIR`, with the default `AgentSettings`. The behaviour settings (planning, limits, approvals, SearXNG, log level) are set in the app; apps merge the saved ones (`store.settings`) over this per run.
- **Token usage**: every model call goes through `callRecorded` in `agent.ts`, which times it and records it on the run's `Budget` (`RunResult.calls`: kind, model, duration, tools asked for, tokens) with what its tokens went to (`usage-breakdown.ts`: `inputBreakdown` by system prompt section (`systemPromptSections` in `prompt.ts`), tool definition, the user's words vs context the app added, notes, summary, earlier turns, each tool result and images; `outputBreakdown` by reply text, tool calls and the rest as reasoning). The server reports totals only, so parts are counted like the context meter and scaled to them. A call the server reports no tokens for is counted from its unscaled parts and marked `isEstimated`, so run totals and the token budget include it; `@app/db` does the same for runs saved before. After each call it emits a `usage` event (the run's steps and tokens so far), so apps can show them live. While a call streams it also emits them with `isEstimated` (at the start, then at most every 250 ms): the request counted from its parts, the output from what has streamed (`ModelRequest.onOutput`, which `llm.ts` calls for text, refusals, tool calls and reasoning text, at ~4 characters a token); the event at the end has the server's counts. Reasoning a server doesn't stream isn't counted until then.
- `title.ts`: `suggestChatTitle(callModel, userMessages)`, a short tool-free call that names a chat, and `cleanTitle` for its reply.
- `improve.ts` / `write-instructions.ts` / `improve-skill.ts`: one tool-free call each, for the composer's improve button, the workspace form's instructions assistant and the skill form's Improve (`improveSkill`: instructions plus a suggested description, as JSON) (`writeInstructions`; the project summary it gets is marked as data).
- `memory/`: `short-term.ts` (the conversation, append-only so servers can cache prefixes), `long-term.ts` (`MemoryStore` interface, the JSON `LongTermMemory` the app uses as `.code-ai/<workspace>/memory.json`, keyword ranking). `file-io.ts`: atomic writes and per-file queues.
- `mcp/`: MCP servers as tools. `hub.ts` (`McpHub`) starts and reuses each workspace's servers, kept per workspace id (several workspaces can share a folder) and run in its folder (stdio, Streamable HTTP with SSE fallback), restarts them on config change and stops idle ones; `tools.ts` turns their tools into `AnyTool`s (`mcp__<server>__<tool>`, approval unless auto-approved). Passed to the loop as `createAgent({ extraTools })`. They are deferred (`buildToolset`: `deferred`, `deferredSummary`, `definitionsFor(loaded)`): the system prompt lists them by name and first sentence, and only the ones the model loads with `load_mcp_tools` (exact names, or a prefix ending in `*`) are sent as definitions, for the rest of the run. MCP tools the chat already called are loaded at run start, so its history matches the tools sent. MCP schemas are large (Atlassian's 26 tools are ~70K characters), so don't send them eagerly.
- `attachments.ts`: the `AttachmentStore` interface for files the user attached (kept by `@app/db` in `.code-ai/<workspace>/uploads/`), passed as `createAgent({ attachments })`; `agent.run(prompt, { attachments })` lists them after the message. `tools/attachments.ts`: `read_attachment` (PDF via `unpdf`, `.docx` via `mammoth`, text), `view_image` (queues the image; the loop adds it as an internal user message with `images: [id]` after the tool results, and `llm.ts` sends it as an `image_url` part) and `save_attachment` (needs approval).
- `skills.ts`: the `SkillStore` interface for the workspace's skills (kept by `@app/db` in `.code-ai/<workspace>/skills/<name>.md`, or `<name>/SKILL.md` plus files for an uploaded skill folder), passed as `createAgent({ skills })`. Each run lists them in the system prompt and the planner input (`renderSkills`: name and description, read at run start); `use_skill` (`tools/skills.ts`, read-only) loads one in full and lists its files (`skillFilesNote`). The file tools can't reach `.code-ai/`, so a skill's files go through `SkillStore.readFile`: `read_skill_file` (read-only) and `copy_skill_file` (asks first, `files` group) only see files listed in `Skill.files`. `agent.run(prompt, { skills })` adds the skills the user picked after the message (`pickedSkillsContext`) and saves their names on it (`skills` on the user message).
- **Tool groups**: `buildToolset(extra, disabledGroups)`. A workspace can turn off `files`, `commands`, `web`, `memory`, `plans` (`TOOL_GROUPS` in `@app/shared`, `GROUP_OF` in `tools/index.ts`): their definitions aren't sent, `basePrompt(off)` in `prompt.ts` leaves out their guidance (with every group on it is the full `SYSTEM_PROMPT`, word for word), and a call to one refuses. Attachment tools are sent only when the chat has files, `use_skill` only when there are skills, MCP tools only once loaded; tools the chat already called are always sent so its history stays valid. `createAgent({ disabledTools })`; `runInChat` passes the workspace's, and its planning choice (`planning: default | auto | off`; plans off means planning off).
- **Steering** (messages the user sends mid-run): `createAgent({ steering })`, a `SteeringInbox` (`take()` hands out the waiting `SteeringMessage`s once each). The loop takes them before each model call (so after a step's tool results, never between a tool call and its result) and once more when the model gives a final answer, which then continues instead of finishing. Each becomes a user message (`steeringMessage` in `prompt.ts` around the text, `display` the text, `steeredAt` the time it was sent, saved in the chat), is appended to the run's `request` (planner, summaries, write-up at the limit), and is reported as a `steer` event. Without `steering` a run reads none (the CLI).
- **Questions** (`tools/ask-user.ts`): `ask_user` asks the user one question with 2-4 options (`QUESTION_LIMITS` in `@app/shared`; labels distinct, checked in code) and waits: `createAgent({ askUser })` (an `AskUserFn`, `ToolContext.askUser`) resolves with a `QuestionAnswer`, an option's label or the user's own words, or `skipped`. The tool tells the model which (picked / own words / skipped: go on and say what you assumed). Without `askUser` it errors so the model asks in its reply. No approval: asking changes nothing. The API answers from the browser (`RunRegistry.createAsker`), the CLI from a numbered prompt; evals pick the first option. The system prompt's "ambiguous request" line points the model at it instead of ending a reply with a question.
- **Voice replies**: `createAgent({ voiceReplies })` (from the workspace's `voiceMode`, via `runInChat`) adds `VOICE_REPLIES` to the system prompt, before the workspace instructions: short spoken sentences, no Markdown, code or URLs read out.
- `tools/`: one file per tool plus the `index.ts` registry; `tools/files/` holds the file tools and `walk.ts` (tree walk, skipped folders, globs); `run-command.ts` runs bash in the workspace (own process group, timeout, leftovers stopped; `tools/shell.ts` holds the shell choice, group signals and the bounded output both it and background tasks use). Live events use `AgentEvent` from `@app/shared`.
- **Context window** (`context.ts`): every model call is kept inside the model's window (`ModelSettings.contextWindow`, or `createAgent({ contextWindow })` in tests, else `DEFAULT_CONTEXT_WINDOW` 128K from `@app/shared`), minus room for the reply (`maxTokens`, at most half; else a tenth). `prepareRequest` in `agent.ts` estimates each request (characters / 4 for system prompt, tool definitions, messages; ~1,500 per image), corrected by the server's reported input tokens (`ContextMeter.calibrate`). At 80% (`COMPACT_AT`) `compact` summarizes the older part of the model's view in one tool-free call per chunk (`COMPACTION_PROMPT`, `transcriptChunks`), keeping the newest ~25% word for word (`compactionCut`, never starting on a tool result); the summary (`summaryMessage`: summary, current plan, saved memories, and this run's request word for word if it was covered) is appended as an internal user message with `summaryOf` (`Conversation.addSummary`), and `Conversation.forModel()` sends it in place of the messages before `summaryOf`. Nothing is deleted, so the chat (and its saved rows) keep everything; the summary rewrites the prompt's start once, so server caching restarts there. Past 95% (`HARD_LIMIT`) the oldest tool results (not the latest batch) are replaced by a stub for that call only (`shrinkToolResults`). Tool output and the memory list are capped relative to the window (`contextLimits`); only images still in the model's view are loaded. Events: `context` after each call (used tokens of the window), `compaction` when it summarizes.
- **Background tasks**: `background-tasks.ts`. `run_command` with `background: true` starts the command as a task (no timeout; it still needs approval) and returns its first 4 s of output; `task_output` (read-only) lists the workspace's tasks or reads one's state and output, `stop_task` (needs approval) ends one and everything it started. The app holds one `BackgroundTasks` for its life and each run gets `forWorkspace(workspaceId, chatId)` (kept per workspace id, not folder: workspaces sharing a folder have their own tasks) as `createAgent({ tasks })` (`ToolContext.tasks`), so a chat only sees its own workspace's tasks. At most 10 run per workspace; the last 10 stopped ones are kept for reading. A task whose shell exits has its leftovers stopped; `close()` / `closeWorkspace()` stop them on shutdown or when a workspace is deleted or moved. Without `tasks` (e.g. a test) background starts refuse.

## Adding a tool

1. Create `src/tools/my-tool.ts` with `defineTool({ name, description, properties, run })`. The description says _when_ to call it: that text is how the model decides.
2. Register it in `src/tools/index.ts`.
3. Set `isReadOnly: true` if it only reads (files, the web, memory) and its result doesn't depend on the order of calls: the loop may run it alongside other read-only calls. Never with `needsApproval` (`defineTool` throws).
4. Set `needsApproval: true` if it changes anything outside the agent (writes files, sends messages, spends money). Such tools (and MCP tools that ask first) automatically get an optional `reason` argument, one sentence for the user that the approval card and CLI prompt show as "Why"; `runValidated` strips it, so `run` never sees it. Arguments the model may leave out go in `optional` (null counts as left out).
5. Add an offline test in `test/` and an eval case in `evals/cases.json`.

`npm run test -w @app/agent` is free (fake model). `npm run eval -w @app/agent` calls the real model named by `EVAL_MODEL` / `EVAL_BASE_URL` / `EVAL_API_KEY` in the root `.env` and costs money.

- **Team (multi-agent)**: with `config.subagents`, `delegate_task` (`tools/delegate.ts`, made per run by `makeDelegateTask(specialists)`) takes `{task, label?, agent?}`. Specialists (`team/specialists.ts`): built-in `general` (default), `researcher`, `coder`, `reviewer`, `writer`, plus `createAgent({ specialists })` (later same-name entries replace built-ins; `@app/db` passes the workspace's `.code-ai/<workspace>/agents/*.md`). `delegate()` gives the child its specialist's tool groups (`specialistOffGroups`, never one the workspace turned off), `readOnly` (`buildToolset` drops `needsApproval` tools and `remember`/`forget`), its role (`systemPromptSections({ team })`), and `model: 'review'` runs it on `reviewCallModel`. Team notes (`team/board.ts`, `tools/notes.ts`): one `Board` per `run()`, shared through `ToolContext.notes` with each note's author (the sub-agent's label). Consecutive `delegate_task` calls in one step run in parallel, at most `config.maxParallelSubagents` (Settings → Agent), splitting the remaining token budget. Prompts take turns (`one-at-a-time.ts`): `ask_user` across the agent and its sub-agents, and `createApprover`'s terminal prompts; the CLI also puts approvals and questions through one shared queue. `ApprovalSource` carries `{ subagent, specialist }`; the API sends `specialist` on the `approval` stream event. Tests: `test/team.test.ts`.
- `tools/plugins.ts`: building tool plugins from the chat. `list_tool_plugins` (read-only, sent whenever the app passes `plugins: PluginWorkshop`) lists the saved plugins or shows one's code, with `PLUGIN_CODE_GUIDE`; calling it makes `test_tool_plugin` (runs draft code once via `testPluginCode`, asks first) and `save_tool_plugin` (saves it, restarts its servers, turns it on in the workspace; asks first) available (`PLUGIN_BUILD_TOOLS`, on demand). `@app/db`'s `pluginWorkshop` supplies the store. Env values never reach the model: `env_from` reuses a saved plugin's.
